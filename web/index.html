Linear-time regular expressions

flatline

A regex engine that cannot be made to blow up — and a debugger that shows you why.

The engines in Python, Java, JavaScript and PCRE all match by backtracking: they commit to one possibility and unwind when it fails. On the wrong pattern that costs exponential time, which is how a single HTTP request takes a service down. flatline simulates every possibility at once, so its worst case and its best case are the same case. Step it below, then race it.

Part one

Step the machine

The pattern is compiled to a small program; every instruction is one NFA state. The VM keeps a list of threads, each parked on one instruction, and advances all of them by one character per step. Scrub through and watch the thread list: it is bounded by the length of the program, so no input can widen it. That bound is the whole guarantee.

The race

Both engines below run the same compiled program and return the same answers. The only difference is strategy. Work is counted in steps rather than seconds so the comparison does not depend on the machine: one step is one thread advance for flatline, one path step for the backtracker. Part three

Two ways to run the same program

The difference is not an optimisation. It is a different thing being carried through the input.

Backtracking — carries a path

One guess at a time

At every split the matcher takes the preferred arm and remembers the other one. If the preferred arm eventually fails, it unwinds and tries the alternative. The state it carries is a single path through the pattern, plus a stack of the choices it has not tried.

For (a+)+b against a run of as with no b, every way of splitting those as into groups is a distinct path, and the matcher must exhaust all of them before it can report failure. There are 2n-1 of them. At n = 30 that is half a billion, and the request never returns.

This is what Python, Java, JavaScript, .NET, Ruby and PCRE all do, and why ReDoS is a vulnerability class with its own CWE.

Pike VM — carries a set

All guesses at once

At every split the VM follows both arms and keeps both threads. All threads sit at the same input position and advance together, one character per step. The state it carries is a set of instructions, not a path.

Two threads on the same instruction at the same position will behave identically from there on, so the second is discarded. That single rule caps the thread list at the length of the program, whatever the input. Work per character is therefore bounded, and total work is len(text) × len(program).

The cost is real but bounded: no backreferences, ever. A backreference makes the language non-regular, and no NFA simulation can evaluate one in linear time. flatline refuses them at compile time rather than silently giving up the guarantee.
